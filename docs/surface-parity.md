# Surface parity

This page records what each user-facing Specola surface does on each
bundled adapter, as measured. It is the output of sub-project 1 of the
adapter parity program
and the baseline that sub-projects 2 to 5 are scoped from. Signal
coverage per adapter is in [Adapter capabilities](adapter-capabilities.md)
and is not restated here.

The matrix below is the re-audit of 2026-10-13 on branch
`adapter-parity` at `e607e41`, every adapter at 20 steps per run cell
(RoboCasa at 5), after the defects the first measurement found were
fixed. The `run-hold` and `run-replay` cells of every adapter, and
RoboCasa's `run-random`, were re-taken on 2026-10-14 at 20 steps, at
`8fee091` with the driver changes committed beside this page, when state
replay landed. The history of what changed between the first measurement
(2026-10-02) and this one is at the end of the page.

Each cell is one CLI command run in the adapter's own conda environment
by `benchmarks/parity_audit/audit.py`. The driver assigns a provisional
value by fixed rules; the final value was assigned by reading the log
and record of each cell, under the rules in the
audit plan.
Both values are shown. The matrix and evidence tables are generated by
`benchmarks/parity_audit/render_matrix.py`, which also holds the final
values and their reasons. What was available in the session is in
preconditions.

## Cell values

| Value | Meaning |
|---|---|
| pass | The surface did what its documentation says |
| fail | It raised or produced wrong output; the verbatim error is recorded |
| refused | The adapter rejected the request with a message; the verbatim message is recorded |
| silently ignored | The flag or mode was accepted and had no effect |
| not applicable | The simulator has no such capability; the reason is recorded |
| not exercised | The cell could not be run in this session; the blocker is recorded |

`not exercised` is never a pass.

## What the matrix shows

Every one of the nine simulator adapters starts from the CLI and runs
`discover`, `check`, `write-specs`, `run` in its supported modes, both
terminal UIs, `--web`, `view` and (where the environment has the
`report` extra) `report`. No cell is `silently ignored`: every mode or
flag an adapter does not implement is refused with a message that
names the adapter and what to use instead.

What is not a pass, and why:

- `--render` fails on the five MuJoCo adapters: the viewer window
  opens, then the run fails under the native guard (#129). Viewer
  parity was dropped from the program on 2026-10-02, so this stays
  open at low priority. The other adapters refuse the flag because
  they have no viewer.
- `report` is refused in the `carla`, `isaacsim` and `RoboDojo`
  environments, which lack the `report` extra (#134). A fresh install
  with the adapter's extra has it.
- `run --mode random` is refused on `pybullet` (a URDF scene declares
  no action space), `robodojo` (actions are per-robot command
  dictionaries) and `isaaclab` (FORGE's action box is unbounded, so
  there is nothing to sample uniformly); all three support `hold`.
- `run --mode replay` replays a Specola state recording on the seven
  adapters with a state tier (`libero`, `robocasa`, `metaworld`,
  `dmcontrol`, `mamujoco`, `pybullet`, `isaaclab`). Each `run-replay`
  cell replayed, in a fresh process, the recording its adapter's
  `run-hold` cell wrote, completed all 20 steps, and then passed the
  paired harness (`benchmarks/replay_fidelity.py`), which compares 20
  live observations with their restored states key by key. Every state
  key (joint positions and velocities, controls, time, geometry
  distances, the entity population) was equal on every step, bit for
  bit, except three `pybullet` base quaternion components that came
  back within the 4-ulp tolerance the harness declares for a quaternion
  read back through a rotation matrix. When these cells were taken, the
  kinematic keys (body poses and velocities) on `libero`, `robocasa`,
  `mamujoco` and `pybullet` differed by the live kinematic lag: a live
  observation read them one physics substep behind its joint positions,
  a replayed one at the joint positions. Since 2026-10-14 live
  observations refresh kinematics first, and the paired harness found
  those keys equal on all four (30 steps; the evidence pages'
  "After the kinematics refresh" sections); the cells were not re-taken.
  On `metaworld` and `dmcontrol` they are equal, and on `isaaclab` they
  are within the declared float32 tolerance (1e-6 m). Step outputs
  (contact forces, accelerations) differ on every adapter, because a
  restore does not carry them. The evidence pages give the numbers per
  adapter; the detail line of each cell gives this run's.
- `run --mode replay` is refused on `carla` and `robodojo` with "it has
  no state tier", after a restore probe on each: CARLA's `get_*` calls
  return the last tick's values, so a restore without a tick changes
  nothing the observation reads, and RoboDojo's bowls and camera stand
  are outside the Isaac Lab scene state, so a restore leaves them where
  they are. `mock` and `dataset` have no simulator state. Robomimic
  HDF5 demonstrations stay the native replay path on `libero` and
  `robocasa`, and a `--demo` under any other mode is refused everywhere.
- One `pybullet` `web` cell failed on its first run because the
  driver's Socket.IO probe process produced no output; the cell passed
  on re-run and the driver now records the probe's stderr. The cause of
  the first failure is not known.

Under the descoped criterion of the 2026-08-20 amendment to the
fidelity certification spec, the nine simulator adapters are official
as of 2026-10-13: `libero`, `robodojo`, `metaworld`, `dmcontrol`,
`mamujoco` and `robocasa` through the extraction programme's guards
(the MuJoCo family on reviewed custody rows for MuJoCo 3.3.0, 3.3.1,
3.8.1 and 3.10.0), and `pybullet`, `carla` and `isaaclab` on the legacy
capability wire by scope decision (#111, #112, #107 stay open). `mock`
and `dataset` are internal adapters for development and debugging.
